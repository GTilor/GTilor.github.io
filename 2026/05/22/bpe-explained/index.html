BPE技术详解：LLM的数据处理第一步

本文最后更新于 2026-06-26T16:59:52+08:00

前言

上一篇blog我们从零拆解了一个nanoGPT，但nanoGPT的每一步都藏着巨大的探究学问，这个博客将讲述如何将我们日常看到的文本转化为机器和模型能看得懂的文本。

一、编码基础：字符如何变成字节流

人类的一切文本，在计算机底层都是一个取值范围为
{0,1,…,255}\{0,1,\dots,255\}{0,1,…,255} 的整数序列。所以问题是如何把字符变成数字呢？其实可以分两步：

  • 1.给每个字符分配一个编号，也就是对每个字符分配一个，让他们一一对应————这是 ASCII / Unicode 干的事。
  • 2.把编号变成实际的字节序列存到硬盘上————这是 UTF-8 干的事

1.1 ASCII 与 Unicode

ASCII

ASCII是最早的方案，覆盖了英文字母、数字和标点符号等等，总共128个字符，编号从0到127，这样就把每一个字符映射到了数字。128个数字用7个比特就够了，因为27=1282^7=12827=128，但是实际存储用1个字节（8bit），最高位（第 8 位）恒为 0。

但是ASCII的方案缺点很明显，无法适配全世界各种各样的语言。因此又了Unicode。

Unicode

Unicode的方法很简单：为人类已知的每一个符号分配一个唯一的整数编号，码点空间：U={0,1,…,1114111}U=\{0,1,\dots,1114111\}U={0,1,…,1114111}，写成十六进制就是 U+0000 到 U+10FFFF，所以这些码点其实根本很难用完。

ASCII方案其实是Unicode方案的子集，他们的前面128个码点的对应关系完全一致。

1.2 UTF-8：可变长编码的精巧设计

Unicode的最大码点来到了1,114,111，需要21bit才能存完所有的Unicode码点，那如果每个字符都需要用3个字节来存储的话，那相比ASCII来说，英文和数字简单字符的存储体积需要3倍以上的内存容量。

UTF-8的设计思路:既然ASCII代表常见的字符，那我们希望常见的字符用更少的字节存储，罕见的字符用更多的字节存储。所以本质上是一种变长编码。

编码规则如下表所示，L(c)L(c)L(c)为所需要的字节数：

二、Byte-level BPE 算法：从压缩到分词

2.1 为什么需要 BPE：char-level 的局限

回顾 nanoGPT 的 char-level：每个字符一个 token，词表小（~65），但序列极长，语义稀疏，Attention 的 O(N^2) 复杂度成为瓶颈。word-level 则词表爆炸且有 OOV 问题。BPE 是两者之间的折中。

2.2 Byte-level BPE：基础词表从数万压缩到 256

形式化定义：

  • 基础词表 V0=0,1,…,255V_0 = {0, 1, \dots, 255}V0​=0,1,…,255
  • 目标词表大小 VtargetV_targetVt​arget，目标词表的大小。
  • 合并次数 k=Vtarget−256k = V_target - 256k=Vt​arget−256
  • 每一步：找到语料中出现频率最高的相邻 pair，合并为新 token，加入词表
  • 合并准则：argmax count(pair)\text{argmax } count(\text{pair})argmax count(pair)，纯频率统计，相同数量的词保留靠前的。

后续合并的规律

如果继续做下去，BPE 会逐渐发现：

最终，高频词 "the " 可能被编码为 1 个 token，“bee“ 被编码为 1 个 token，而从未在训练集中出现过的新词（比如 “flee“）则回退到字节级编码：[102, 108, 101, 101]——这就是 Byte-Level BPE 的 OOV 免疫能力。

手推的收获

通过这个例子，我们亲眼看到了三个关键现象：

  1. BPE 是纯频率驱动的：它不知道 “the“ 是英语单词，不知道空格是词边界，它只看到 “101, 32“ 这个 pair 出现了 6 次，所以先合并它。

  2. 合并是递归的：Step 1 合并出 256 ("e ")，Step 3 才用 256 和 257 (“th“) 合并出 258 ("the ")。每次合并都在前一步的产物上继续构建。

  3. 新 pair 在合并中涌现：Step 1 之前，(h, 256) 这个 pair 不存在。合并 (e, ’ ') 之后，h 后面紧跟 256，这个新 pair 就"涌现"出来了。BPE 必须在每一步重新统计频率，因为序列结构在不断变化。

三、BPE 的数学证明与信息论视角

3.1 BPE 的本质：贪心无损压缩

BPE 的每一步合并都在缩短序列长度，本质上就是在做贪心压缩。和 Huffman 编码的区别：Huffman 是最优前缀码，BPE 不保证最优，但 BPE 产出的是可学习的 token 序列而非比特流。

3.2 BPE vs WordPiece vs Unigram：三种 Subword 算法辨析

算法 合并/分割方向 合并准则 代表模型
BPE 自底向上合并 argmax count(pair)，纯频率 GPT-2/3/4, LLaMA
WordPiece 自底向上合并 近似最大化训练数据似然（≈PMI） BERT
Unigram 自顶向下裁剪 最小化移除后的语言模型损失 SentencePiece, T5

关键区分：BPE 用的是频率，WordPiece 用的才是类 PMI 准则，Unigram 是概率模型。三者不可混淆。

六、分词的前沿思考

虽然 Scaling Law 使得模型在参数量和训练数据规模的暴力增长中能够克服诸多底层表征的瑕疵，但分词器（Tokenizer）的设计依旧是多语言处理、工程效率以及精密推理的核心瓶颈。从信息论与学术实证的角度来看，传统的 BPE 分词在以下三个关键维度正面临严峻挑战。

6.1 中文与多语言：UTF-8 编码导致的分词偏置

1. 学术实证与瓶颈

在多语言场景下，BPE 最致命的缺陷在于跨语言的信息密度失衡。

  • 文献支撑：Petrov et al. (2023) 在论文 Is tokenizer bias a bottleneck for multilingual LLMs? 中定量分析了这一偏置。由于 UTF-8 的物理编码结构，绝大多数中文字符需要占用 3 个字节。在英文主导的预训练语料中，这些字节很难在 BPE 的贪心频次统计中获得足够的合并优先级。
  • 后果：这导致同等语义内容下，中文消耗的 token 数量是英文的 2∼3.52 \sim 3.52∼3.5 倍。由于 Transformer 的 Self-Attention 具有 O(N2)\mathcal{O}(N^2)O(N2) 的复杂度，这意味着中文用户在计算开销和推理延迟上承担了数倍的"隐形税"，且模型的有效上下文窗口（Context Window）物理缩水了 60%60\%60% 以上。

2. 工业界改进方案

  • 词表扩展（Vocabulary Expansion）与重平衡：以 Qwen Technical Report (2023) 为代表，现代多语言模型将词表大小由早期 LLaMA 的 32K 直接扩增至 100K 甚至 150K 级别。在 BPE 训练阶段大幅拉高中文语料配比，使得高频汉字及常用词组能一步合并为单一 token，中文单字的平均 token 消耗得以缩减至 ~0.6。

6.2 代码：语法树（AST）割裂与格式冗余

1. 学术实证与瓶颈

代码文本具有强结构性与高局部重复性，而通用 BPE 分词器无法感知抽象语法树（AST）的物理边界。

  • 文献支撑：Li et al. (2023) 在 StarCoder 论文中指出，普通分词器对连续空格（缩进）以及代码关键字与变量的粘连处理极低效。
  • 后果：代码前的大量缩进空格会按长度任意切分（或以单个空格 token 堆叠），造成大量无意义的 token 占用。此外，组合标识符（如 calculateLoss）在词表中被切碎，且在表征空间中与其变体（如 calculate_loss）物理隔离，模型必须在深层重新学习这些在句法上完全等价的结构。

2. 工业界改进方案

  • 缩进专用 Token（Indentation-aware Tokens）：强行在词表中预置专属的缩进 token（例如 <|space_4|>、<|space_8|> 等），将缩进的 token 消耗从 O(L)\mathcal{O}(L)O(L) 降低为 O(1)\mathcal{O}(1)O(1)。
  • 词法分词限制（Lexer-based Rules）：利用正则或词法分析器，在预分词阶段禁止跨单词/符号边界进行贪心合并，保证 def、return、操作符（如 +=）的结构独立性。

6.3 推理与数学：数值非连续表征与形态学盲区

1. 学术实证与瓶颈

这是 BPE 在逻辑与计算任务中最为严峻的局限性。

  • 文献支撑：Nogueira et al. (2021) 在 Teaching Arithmetic to Small Transformers 中指出，数字在 BPE 下根据统计频率的随意切分（例如将 12345 切为 [123] 和 [45]）是阻碍 Transformer 学会大数泛化计算的根本原因。
  • 后果：
    1. 数位无法对齐：不同数字在输入端被切分成非等长的 token 块，使 Self-Attention 无法建立统一的列式对齐加法。
    2. 数值连续性缺失：在 Embedding 空间中，模型难以在底层建立起 [123] 与其他数字的数值拓扑关系。
    3. 形态学盲区（Spelling Blindness）：正如 ByT5 (Xue et al., 2021) 所揭示，诸如 strawberry 被 BPE 切分为 ['straw', 'berry']，剥夺了模型在前几层直接观测底层字符细节的能力，导致在回文检测、拼写检查等任务上面临天然表征缺陷。

2. 工业界改进方案

  • 数字单字符强制切分（Single-digit Split）：在 LLaMA 3 及 GPT-4 的预分词正则中，强行规定所有数字 0-9 必须保持为独立 token，不允许合并为多位数字。这保证了 12345 在输入层恒表示为 [1][2][3][4][5]，直接使模型具备了高泛化性的数学按位推理能力。

6.4 前沿演进：无分词器路线（Tokenizer-Free）

为了彻底根除 BPE 等 subword 算法带来的表征偏置与信息流失，学术界正向着无分词器路线演进。

  • 文献支撑：Wang et al. (2024) 在论文 MambaByte: Token-free Selective State Space Models 中提出了一种完全运行在原始字节流上的无分词器模型。
  • 核心思想：直接以单字节（0-255）作为输入。过去，Transformer 面对超长字节序列时受制于 O(N2)\mathcal{O}(N^2)O(N2) 计算复杂度；而伴随具有 O(N)\mathcal{O}(N)O(N) 线性复杂度的状态空间模型（SSM，如 Mamba）或线性注意力机制的成熟，无分词器架构可以直接处理极长字节流，消除了分词阶段带来的所有信息熵损失。

6.5 推理效率：Token 即成本的商业法则

在训练阶段可以通过 Scaling Law 弥补分词的瑕疵，但在推理阶段，Token 数量直接决定了商业经济成本：

推理成本∝输入 Token 数+输出 Token 数\text{推理成本} \propto \text{输入 Token 数} + \text{输出 Token 数} 推理成本∝输入 Token 数+输出 Token 数

每一次 Tokenizer 效率的提升（例如通过扩大词表减少编码后的总序列长度 NNN），都直接等价于在推理端降低计算开销、提升吞吐量和减少延迟。这也是当前各大主流模型（OpenAI, DeepSeek 等）持续迭代 Tokenizer 核心正则表达式的底层商业驱动力。
